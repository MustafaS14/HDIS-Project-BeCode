# HIDS Bash Project Research
**HIDS Design Philosophy**
Effective Host Intrusion Detection Systems (HIDS)—such as Wazuh, OSSEC, Auditd, and Tripwire—avoid relying on a single metric to detect compromises. Instead, they aggregate multiple evidence sources by scanning relevant files and databases, normalizing data, establishing baselines, and generating alerts only when meaningful deviations occur based on predefined rules.

**System Health Telemetry**
A running Linux system's stability and stress levels can be tracked using specific performance metrics, commands, and kernel pseudo-files:

* **CPU and Load Averages:** Monitored via `/proc/loadavg` (1-, 5-, and 15-minute averages). Upward trends over 15 minutes indicate resource buildup, thread leaks, or I/O bottlenecks.
* **Memory Usage:** Tracked using the `free` command.
* **Disk Storage & I/O:** Monitored via `smartmontools` for component health and `sysstat` (`iostat -xz 1`) for storage activity. Sustained `iowait` above 20–30% warrants a disk or storage investigation.
* **Component Temperatures:** Measured using `lm-sensors`.
* **Network Connections:** Inspected using `ss`.

**User Activity & Authentication Auditing**
Linux records user logins, sessions, and authentication events through native binary logs and plain-text system files:

* **Binary Log Files (`/var/log/`):**
* `utmp` and `wtmp`: Track logged-in users and session history (queried via `last`).
* `btmp`: Records failed login attempts (queried via `lastb` to audit brute-force attacks).
* `lastlog`: Stores the last login timestamp for all system users.


* **Authentication Logs (`/var/log/auth.log` or `/var/log/secure`):** Real-time plain-text logs recording SSH logins, `sudo` usage, account switching, and PAM authentication events with timestamps, usernames, source IPs, and status.
* **Active Sessions:** Viewed via `w` or `who`. Historical records can be filtered using `last -a` or by searching logs (`grep "Accepted" /var/log/auth.log`).
* **Suspicious Activity Indicators:** Execution of discovery commands (`whoami`, `id`, `uname -a`, SUID file scans), unauthorized `sudo`/`su` usage by non-admin accounts, modification of crontabs (`/etc/crontab`, `/etc/cron.d/`), tampering with SSH keys (`~/.ssh/authorized_keys`), clearing history (`history -c`), or process name spoofing.

**Process Telemetry**
Process information is dynamically generated by the kernel inside the `/proc/` pseudo-filesystem directory, allowing inspection without third-party tools:

* **Global Metrics:** `/proc/loadavg` and `/proc/stat` provide low-level CPU and scheduling statistics.
* **Process-Specific Data (`/proc/[PID]/`):**
* `/proc/[PID]/cmdline`: Launch arguments.
* `/proc/[PID]/exe`: Symlink pointing to the physical binary path.
* `/proc/[PID]/status`: Memory usage, state, and User/Group IDs.
* `/proc/[PID]/fd/`: Open file descriptors and network sockets.


* **Inspection Utilities:** `ps -ef`, `pstree`, `top`, `htop`, and standard file-reading tools (`cat`, `less`, `head`).
* **Suspicious Process Traits:** System daemons running under `root` instead of a low-privilege account (e.g., `www-data`, `mysql`), binaries executing from world-writable or temporary directories (`/tmp/`, `/dev/shm/`, `/var/tmp/`), unexpected parent-child hierarchies (e.g., web services spawning terminal shells), and disguised execution paths.

**Network Security & Socket Tracking**

* **Listening and Active Sockets:** Queried directly from the kernel using `sudo ss -tulpn` (-t for TCP, -u for UDP, -l for listening, -p for process name/PID, -n for numeric addresses). Alternatively, `lsof` can track active connections and responsible processes.
* **Network Red Flags:** Traffic on non-standard ports, beaconing signals to external command-and-control servers, and brute-force indicators (sudden spikes in failed logins followed by successful authentication).

**File Integrity Monitoring (FIM)**

* **Critical Files to Monitor:**
* Configuration/Security: `/etc/passwd`, `/etc/shadow`, `/etc/sudoers`, `/etc/ssh/sshd_config`, `/etc/crontab`, `/etc/services`, and `/etc/cron.d/`.
* Binaries: `/bin`, `/sbin`, `/usr/bin`, and `/usr/sbin`.
* Temporary Paths: `/tmp/`.
* Log Files: `/var/log/auth.log`, `/var/log/syslog`, `/var/log/kern.log`, `/var/log/audit/audit.log`.


* **Dangerous Permissions:** Writable password files, world-writable binaries or directories (777 permissions), misconfigured SUID/SGID bits, overly permissive `sudoers` configurations, and writable system scripts executed via cron.
* **Detection Methods:** Utilizing `find` commands (`find /etc -type f -mmin -60`, `find /etc -type f -mtime -1`) or inspecting exact timestamps with `stat`.

**Logging & Alerting Architecture**

* **Default Log Repositories:** `/var/log/auth.log`, `/var/log/syslog`, `/var/log/kern.log`, `/var/log/dpkg.log`, `/var/log/faillog`, and web server logs (`/apache2/`, `/nginx/`). Live streaming and searches are performed using `tail -f`, `grep`, or `journalctl -u ssh`.
* **Structured Alert Components:** Professional security tools format alerts using a Timestamp, Severity/Priority Level, Source IP/Host, Destination IP/Host/Path, Event Type/Signature ID, Impact Description, and Recommended Actions (supported formats include JSON, CSV, XML, Syslog, and CEF).
* **Alert Quality vs. Noise:** Trustworthy detection systems establish performance baselines, enrich alerts with granular contextual metadata ("who, what, how"), tier severities properly, and aggregate related events (e.g., grouping 1,000 failed SSH attempts into a single brute-force notification) rather than flooding logs.
